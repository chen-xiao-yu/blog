# 你按下"发送"，LLM API 调用究竟发生了什么？

你发出一个请求，约 400 毫秒后拿到响应。

看起来很快，但这短短的时间里，你的请求悄悄穿越了 **14+ 层基础设施**，触发了**数十亿次矩阵乘法**，消耗了**每小时数千美元的 GPU 算力**。


下面，我们一层一层拆开来看。

---

## 第 1 步：API 网关（~5ms）

你的请求第一站，不是模型，而是网关。

🔹 TLS 解密终止，建立加密通道
🔹 验证你的 API 密钥是否有效
🔹 限流器检查：你的每分钟 Token 数和请求数是否超限
🔹 校验请求结构（Schema Validation）
🔹 计费计时器，从这一刻开始走

你有没有遇到过莫名其妙的 `429` 错误？那就是在这里被拦下来的。

---

## 第 2 步：负载均衡器（~2ms）

通过网关之后，请求需要被分配到一个具体的 GPU 集群。

🔹 根据你的地理位置，路由到最近的数据中心
🔹 最少连接算法，挑选当前负载最轻的集群
🔹 健康检查在后台持续运行，剔除故障节点

这也解释了一个常见现象：明明是完全相同的请求，延迟却时高时低——因为每次落到的集群可能不同。

---

## 第 3 步：Tokenization 分词（~3ms）

模型不理解文字，只认数字。这一步完成转换。

🔹 根据不同提供商，采用 BPE、SentencePiece 或 WordPiece 算法
🔹 平均每个 Token 对应约 4 个字符
🔹 同时检查是否超出上下文窗口限制

**Token 数量直接决定你的账单**，计费逻辑就跑在这里。

---

## 第 4 步：模型路由器（~1ms）

这是整个链路里最少被人提及的一层，但它真实存在。

🔹 大模型请求 → 路由到多 GPU 重型集群
🔹 小模型请求 → 路由到优化过的轻量集群
🔹 Embedding 请求 → 路由到专用集群
🔹 高峰期流量进入排队机制，削峰填谷

任何提供多个模型的服务商，都少不了这一层调度逻辑。

---

## 第 5 步：推理（~300–800ms）

这里是整个过程的核心，**占据了你等待时间的 95%**。

推理分为两个阶段：

### 预填充（Prefill）

🔹 所有输入 Token 并行处理，一次性"读完"你的 Prompt
🔹 在 Query 矩阵与 Key 矩阵之间计算注意力分数
🔹 生成 KV Cache，存入 GPU 的 HBM 高带宽显存
🔹 Prompt 越长，这个阶段耗时越久，首 Token 时延（TTFT）也越高

### 解码（Decode）

🔹 每次前向传播只生成一个 Token——逐字"写出"回答
🔹 复用 KV Cache，历史 Token 不会被重复计算
🔹 Temperature 和 top_p 在这里控制输出的随机性
🔹 开启流式输出时，每个 Token 生成后立即推送给你

**这就是流式输出存在的根本原因：模型本身就是一个字一个字在生成，没有办法"一次性"给你全部。**

### 支撑推理的硬件

🔹 A100 / H100 / H200 GPU，单卡搭载 80GB+ HBM 显存
🔹 模型权重通过张量并行（Tensor Parallelism）分布在多张 GPU 上
🔹 多个用户请求合并成批（Batching），共享算力、提升吞吐
🔹 Flash Attention 与 GQA 技术优化显存访问效率

这也是 GPU 算力每小时要花 2–3 美元的原因所在。

---

## 第 6 步：后处理（~5ms）

模型输出的是 Token ID，还需要加工一遍才能交给你。

🔹 Token ID 转换回可读文本
🔹 安全分类器对内容进行审查，过滤不合规输出
🔹 检查停止序列（Stop Sequences），决定在哪里截断
🔹 将结果封装成标准 JSON 格式

---

## 第 7 步：计费 & 返回响应

最后一步，结算账单，把响应发回给你。

🔹 输入 Token 数 × 每 1K Token 单价
🔹 输出 Token 数 × 每 1K Token 单价（通常是输入的 3–5 倍）
🔹 开启 Prompt 缓存后，重复内容不再重复计费，成本可以显著降低

---

> 400 毫秒，7 个步骤，14+ 层基础设施。
>
> 下次你调用 API 的时候，不妨想一想，这一切都在背后悄悄发生了一遍。
