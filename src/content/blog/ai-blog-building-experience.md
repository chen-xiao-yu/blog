## 起因

我一直想有一个自己的技术博客，但每次想到要折腾框架、配样式、搞部署，就劝退了。作为一个 Java 开发者，前端不是我的强项，更别提还要兼顾设计、响应式、SEO 这些事情。

直到最近，我尝试了一种新的方式：**全程用自然语言和一个 AI 助手对话，让它帮我完成所有开发工作**。

结果出乎意料——不仅做出来了，而且效果还不错。

## 技术栈是什么？我自己定的

一开始我没有指定任何技术栈，而是把自己的需求用大白话告诉了 AI：

> 我想做一个个人技术博客，要好看、要快、要好维护、要免费部署

AI 给了我一个对比方案：

| 方案 | 优势 | 劣势 |
|------|------|------|
| Next.js | 生态强大，SSR 成熟 | 对纯内容站偏重 |
| Hugo | 构建极快 | 模板系统学习成本高 |
| **Astro** | 内容优先，轻量快速，输出静态 HTML | 动态交互需额外处理 |
| VitePress | 文档向 | 偏文档站，博客定制弱 |

我选了 **Astro**——理由很简单：我是写文章用的，不是做 Web App，Astro 的「默认零 JS」理念正好契合。

## 整个过程像在和一个高级工程师聊天

### 第一步：项目初始化

我只说了一句：「用 Astro 搭建一个现代风格的个人博客」，AI 就帮我完成了：

- 项目初始化（`npm create astro@latest`）
- 目录结构规划
- 全局样式体系（CSS 变量 + 设计 token）
- 响应式布局

我完全没有碰过终端（当然，AI 帮我跑的命令除外）。

### 第二步：页面开发

接下来就是一轮又一轮的对话：

**关于首页：**
> 「首页要有一个 Hero 区域，展示博客名字和简介，下面是文章列表」

AI 给我做了带渐变背景的 Hero 区域、卡片式文章列表，还自动适配了手机端。

**关于文章详情页：**
> 「文章页要有目录导航、代码高亮、阅读进度条」

AI 加了侧边目录（后来我觉得位置不合适去掉了）、Shiki 代码高亮、顶部阅读进度条。

**关于交互功能：**
> 「我想加个微信分享功能，扫码分享到朋友圈」
> 「再加个公众号关注弹窗吧」

AI 实现了两个精美的 Modal 弹窗，带二维码位、ESC 键关闭、点击遮罩关闭等细节。

### 第三步：迭代优化

最有意思的是迭代过程。每次我说「感觉这里可以更好」，AI 就会给出方案让我选：

**标签功能的演进：**

> 「标签页放在独立页面太深了，能不能放到首页？」

AI 给了我 5 个方案：

| 方案 | 思路 | 评价 |
|------|------|------|
| A | Hero 下方加标签快捷栏 | ⭐ 推荐：直观，移动端可横滑 |
| B | 标签放导航栏下拉 | 不占空间，但多一层交互 |
| C | PC 侧边栏标签云 | 经典布局，但改动大 |
| D | 前端筛选不跳转 | 体验最流畅 |
| E | 首页 Tab 切换 | 整合度高 |

我选了 **A + D 组合**：首页 Hero 下方加标签胶囊栏 + 点击实时过滤文章列表。PC 端整齐排列，手机端横向滑动。

**其他优化：**

- 弹窗提示文字加粗 → AI 直接改了，顺便加了 ESC 关闭
- 导航栏多余的「标签」链接 → 去掉，因为首页已经有了
- 数字 badge 看不见 → AI 发现 CSS 的 `opacity` 属性重复声明导致覆盖，修复后清晰可见

### 第四步：部署上线

> 「部署选哪里好？GitHub Pages？Netlify？Vercel？」

AI 帮我对比了三个平台，最终选了 **Netlify**——域名好看、部署预览功能强、CMS 集成方便。而且配置了 Decap CMS，以后可以直接在网页上写文章，不用本地构建。

## 遇到的坑？有，但都不是我的问题

整个过程中确实遇到了一些技术问题，但**每一个都是 AI 发现并解决的**：

| 问题 | 原因 | 解决 |
|------|------|------|
| 标签包含 `/` 导致路由失败 | Astro content collection 的 glob 匹配把路径符号当分隔符 | 标签名避免特殊字符 |
| `<ul>` 内嵌套 `<li>` 导致筛选失效 | 非法 HTML 结构被浏览器强制"修复"，JS 找不到正确元素 | 改为 `div` 容器 |
| CSS `opacity` 重复声明 | 两行 `opacity` 后面的覆盖前面的，badge 几乎不可见 | 重构为独立的背景色+边框样式 |
| Node 版本不兼容 | Astro v6 要求 Node 22+，系统只有 20 | AI 自动安装了 managed Node 22 |

注意上面的关键点：**我不需要知道这些问题的存在**。AI 在构建时发现报错，自己分析原因，自己修好，然后告诉我「搞定了」。

## 这种开发方式靠谱吗？

说实话，一开始我也怀疑。但实际体验下来，有几个明显的感受：

**1. 门槛真的降低了**

以前做一个博客，至少得会：HTML/CSS/JavaScript/包管理/构建工具/部署流程。现在你只需要**说清楚你想要什么**。

**2. 迭代效率很高**

传统开发中，改个样式可能要：想方案 → 写代码 → 刷新看效果 → 不满意再改。现在变成了：说需求 → 看效果 → 说调整。中间的编码环节被压缩到了近乎为零。

**3. AI 不是万能的**

也有不太顺的时候。比如标签筛选功能第一次没实现出来，原因是 HTML 结构嵌套错误。AI 排查了两三轮才定位到问题。但这恰好说明——**它在调试排错方面确实像一个真正的开发者**。

**4. 适合的场景**

这种方式特别适合：
- 快速原型验证（「先做个 demo 看看」）
- 非主 tech stack 的开发（Java 开发者做前端）
- 个人项目 / Side Project
- 学习新技术（让 AI 边做边解释）

不适合的可能是：
- 复杂业务逻辑（需要深入理解领域）
- 团队协作规范（code review、CI 质量门禁）
- 性能极致优化的场景

## 写在最后

这篇文章本身，也是在这个博客上发布的。某种程度上，这是一篇「元博文」——用这个博客来记录它的诞生过程。

如果你也想试试这种开发方式，我的建议是：

1. **先把需求想清楚**——模糊的需求得到模糊的结果
2. **分步骤来**— 不要一次丢一大堆需求，逐步迭代效果更好
3. **敢于说「不对」**——不满意就直接说，AI 会根据反馈调整
4. **让它解释**——不懂的地方问为什么，很多坑就是这样避开的
